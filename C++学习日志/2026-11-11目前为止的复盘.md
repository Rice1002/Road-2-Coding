## 一.C++与C的区别
大一上主要学习了C语言，这是一门非常基础的语言，它没有面向对象的概念，但是他也是一个很重要的语言，如今很多编程语言都是基于C语言编写的。

C++和C的区别主要在于C中并没有面向对象的概念，它是一门过程型的编程语言，核心在于'函数'，主要关注于怎么做，它的数据与数据处理是分离的。而C++则是在C的基础上增加了面向对象的概念，核心是'类'和'对象'，它强调把数据以及对数据的处理方法封装起来，使得代码更加模块化、复用性更强。

但是这并不意味着C语言一无是处，C语言在很多方面仍然非常有用，它是一门更加底层的语言，适合用来写操作系统的内核、单片机的驱动等对性能要求极高的场景。而C++在C的基础上做了大量扩展，既有底层操控能力，又有高级语言的开发效率，更适合开发大型软件（比如游戏引擎、桌面应用、鸿蒙的部分底层库等）。C++的底层内存模型和指针操作是和C一脉相承的，所以学习C对一个刚迈入计算机世界的人来说是非常有必要的。
### 1.内存管理机制
这是C与C++在底层的显著区别，决定着程序的性能与安全。
#### 动态内存分配方式
* **C语言**:使用库函数 malloc()、calloc()、realloc() 分配或调整内存，使用 free() 释放。
    * `malloc(size)` 分配 size 字节的 **原始内存** ，不初始化，也不调用任何构造函数；失败返回 NULL。
    * `calloc(n,size)` 分配 n * size 字节内存，并**初始化为全 0**；失败返回 NULL。
    * `free(ptr)` 释放由 `malloc`、`calloc` 或 `realloc` 分配的内存。
    * `malloc`等`返回void*`。C语言允许`void*`隐式转换为其他对象指针，所以通常我们并不进行强制转换；但一般也不建议进行强制转换，以免掩盖未包含`<stdlib.h>`等错误。
* **C++**:引入关键字 `new` 和 `delete`，把"内存分配/释放"和"对象构造/析构"结合起来。
    * `new`不仅分配内存,还会**自动调用对象的构造函数**进行初始化;失败的时候会默认抛出`std::bad_alloc`.
    * `delete`会先**自动调用对象的析构函数**清理资源,再释放内存.
    * 数组分配释放必须配套使用:`new[]`配`delete[]`,`new`配`delete`.
    * C++中`void*`并不能隐式转换为具体类型指针,核心原因在于**类型安全**,使用`malloc`必须进行显示转换,例如`static_cast<T*>(std::malloc(...))`.
    * `malloc/free`只管理**原始内存**,不调用构造/析构函数;`new/delete`管理**对象生命周期**.二者是不能混用的,比如不能用`free`释放`new`出来的对象.
    * 但是现代的C++更推荐使用智能指针和标准容器来管理资源,减少手动的`new/delete`.
    >`void*` 是一个“无类型”指针，它只记录了一个内存地址，却完全丢失了这块内存的大小、对齐方式和有效类型等关键信息。如果允许它隐式地变回具体类型，编译器就失去了发现错误的机会。考虑一个经典的例子：
    ```cpp
    short s = 10;           // 在多数平台上占 2 字节
    void* p = &s;           
    long* l = p;            // C++ 禁止：隐式转换
    // ...
    *l = 0x1234567890;      // 向一个 2 字节的对象写入 8 字节的数据
    ```
    >在 C 语言中，这段代码可能静默通过编译，结果却是内存越界写入，引发未定义行为。而在 C++ 中，编译器会直接报错，将潜在的内存破坏风险扼杀在编译阶段。强制转换 long* l = static_cast<long*>(p); 并非让这个操作变得“正确”，而是要求程序员明确承认：“我知道这里在进行一个不安全的类型转换.”
#### 内存分配失败的处理
* **C语言**: `malloc` 分配失败时返回 `NULL`，需要通过 `if (p == NULL)` 来检查。
* **C++**：`new` 分配失败时，默认会抛出 `std::bad_alloc` 异常（也可以使用 `new (std::nothrow)` 使其返回 `nullptr`）。

### 2.语言语法特性差异
#### 引用 (Reference) vs 指针 (Pointer)
*   **C语言**：只有指针 `*`，操作底层内存地址，容易发生**空指针**或**野指针**问题。
*   **C++**：引入了引用 `&`。引用是变量的**别名**，必须**在定义时初始化**，且**一旦绑定不能更改指向**。引用在底层通常由指针实现，但在语法层面更安全、更优雅（常用于函数传参和返回值，避免拷贝）。
#### 函数扩展
*   **函数重载 (Overloading)**：C 语言**不支持**同名函数；C++ 支持在同一作用域内定义多个同名函数，只要它们的参数列表（类型或个数）不同即可。
*   **默认参数 (Default Arguments)**：C 语言不支持；C++ 允许在函数声明时给参数指定默认值，调用时可省略该参数。
#### 类型转换安全
*   **C语言**：强制类型转换非常暴力，如 `(int)3.14`，容易引发底层数据截断且难以排查。
*   **C++**：引入了 4 种明确的类型转换操作符，更安全、意图更清晰：
    *   `static_cast`：基本类型转换、父子类指针转换（无运行时检查）。
    *   `dynamic_cast`：主要用于多态类型的向下转换（有运行时检查）。
    *   `const_cast`：去除或添加 `const` 属性。
    *   `reinterpret_cast`：底层的重新解释（类似 C 的强转，极其危险）。
#### const的进化
*   **C语言**：`const` 修饰的变量本质上仍是一个只读变量，可以通过指针绕过修改。且不能用于定义数组长度（C99 变长数组除外）。
*   **C++**：
    *   `const` 修饰的变量具有真正的常量属性，编译器会进行常量折叠（类似 `#define`），可作为数组大小。
    *   引入了 `constexpr`（C++11）用于编译期常量计算。
    *   支持**常量成员函数**（`void func() const;`），承诺不修改对象状态。
#### 字符串
*   **C语言**：没有原生的字符串类型，使用以 `\0` 结尾的字符数组 `char str[]`，需要频繁调用 `<string.h>` 中的函数（如 `strlen`, `strcpy`），极易发生越界和内存泄漏。
*   **C++**：引入了 `std::string` 类，内部封装了内存管理，支持 `+` 拼接、动态扩容，极大地提高了字符串操作的安全性。
####  结构体 (struct)
*   **C语言**：`struct` 只能包含数据成员，不能包含函数，也不能继承。
*   **C++**：`struct` 几乎等同于 `class`，可以包含成员函数、构造函数、支持继承和多态。唯一的区别是 `struct` 默认的成员访问权限是 `public`，而 `class` 默认是 `private`。

### 3.底层与编译机制

*   **名字修饰 (Name Mangling)**：C 语言编译时，函数名就是函数名；C++ 为了支持函数重载，编译器会对函数名进行“名字修饰”（将参数类型等信息加入符号名中）。这也是为什么在 C++ 中调用 C 语言的库时，必须加上 `extern "C"` 的原因——为了防止 C++ 编译器把 C 的函数名修饰得面目全非。
*   **异常处理**：C 语言通常用函数返回值（如 `-1`）表示错误；C++ 引入了 `try-catch` 结构化异常处理，将错误处理与正常逻辑分离。

### 构造\析构函数
*   **作用**：在对象创建时自动调用，用于初始化对象的数据成员。
*   **特点**：
    *   函数名与类名完全相同，没有返回值（连 `void` 都不写）。
    *   可以重载（可以有多个不同参数的构造函数）。
    *   支持**初始化列表**（推荐使用，效率更高，尤其是对 `const` 成员和引用成员）。
*   **特殊构造函数**：
    *   **默认构造函数**：无参数的构造函数（如果不写，编译器会自动生成一个空的）。
    *   **拷贝构造函数**：用同类型的对象初始化新对象时调用。(这部分我还不太懂)
### 析构函数
* **作用**：在对象生命周期结束时（比如作用域结束、 delete 时）自动调用，用于清理资源.

* **特点**：函数名为 ~类名，没有参数，没有返回值。不能重载.

### 类的继承
* **概念**:允许我们根据一个类(基类/父类)来定义另一个类(派生类/子类),子类自动继承父类的属性以及方法.
* **继承方式**:`public`,`protected`,`private`.
* **构造与析构的顺序**：

    构造顺序：基类构造函数 -> 派生类成员变量构造 -> 派生类构造函数。

    析构顺序：与构造顺序完全相反。派生类析构 -> 派生类成员变量析构 -> 基类析构。

### 多态
* **概念**:同一个接口,使用不同的实例而执行不同的操作.通俗的说,就是"父类的指针或引用,指向一个子类对象,调用同名方法时,表现出子类的行为".
* **分类**:
    静态多态（编译期）：函数重载、模板。编译器在编译时就知道调用哪个函数。

    动态多态（运行期）：通过虚函数 (virtual) 实现。编译器在编译时不知道调用哪个函数，在运行时根据对象的实际类型来决定。
### 虚函数
* **作用**：实现动态多态的关键。在基类中声明函数时加上 virtual 关键字。
* **底层原理**:
    当一个类包含虚函数的时候,编译器会为这个类生成一张**虚函数表**,表中存放着虚函数的地址.

    该类的每个对象内部都会有一个**虚表指针**,指向这个表.

    当基类的指针/引用调用虚函数的时候,程序会在**运行时**通过`vptr`找到对应对象的`vtable`,从而调用正确的函数.

    >纯虚函数与抽象类：
    >>virtual void func() = 0; 这叫纯虚函数。

    >>包含纯虚函数的类叫抽象类，不能实例化（不能创建对象），只能作为接口被继承。子类必须实现所有的纯虚函数才能被实例化。

    >虚析构函数：
    >>如果基类的析构函数不是虚函数，当使用 delete 删除一个指向子类对象的基类指针时，只会调用基类的析构函数，导致子类特有的资源（如子类 new 的内存）无法释放，造成内存泄漏。

    >>原则：只要一个类可能作为基类被继承（只要类里有虚函数），它的析构函数必须是虚函数（virtual ~类名() {}）。

我个人觉得,继承与多态才是面向对象的精髓所在啊!

## 三. 一些碎碎念

> **纸上得来终觉浅，绝知此事要躬行。**

这句话放在编程领域是再正确不过的话。看上一千一万遍理论，都不如自己动手跑一遍来得实在。只有自己亲手试着去 Debug，去写去改代码，查看不同之处，才能真正地理解这些东西。

这也是我觉得当今这个行业在人工智能冲击下比较重要的一部分。可能有些人觉得：AI 什么都会了，我只需要把我的任务派给它不就好了吗？

也许确实如此，但我始终觉得**能够把问题描述清楚是一个很强大的能力**。如果你不明白这些底层的东西，没有亲手体验不同的地方，一旦选用了错误的底层逻辑，那么就算 AI 给你做出了多么美丽精妙的城堡，都是一个屎山。

当然，我现在写的这些东西并不算能够导致城堡变成屎山的东西，但真正的点在于：**你能否拥有工程能力。**

> **AI 当然可以给你一个完美的答卷，但是你真的拥有阅卷的能力吗？当阅卷人判断不出答题人答案的正确性之时，才是真正失去能力。**

如今不少人使用 AI 编写代码，但其实只是在玩一场“俄罗斯轮盘赌”。我自己也试过使用 AI 进行编写安卓 APP，但其实我一点都不懂安卓开发。整个开发过程是十分艰难的：我不知道怎么样去描述我的需求，不知道怎么样去选择技术栈与实现，不知道哪种实现方式更适合我的项目需求，我甚至都不知道怎么给它描述 Bug！这是一件很恐怖的事情。

如果 AI 跑通了代码，觉得自己牛逼、AI 牛逼；如果没跑通，甚至自己连报错信息都看不懂，只能让 AI 自己修。但一旦 AI 的修复方向错误，那么这个项目就会越来越歪。当然，如今人工智能正在发展中，我相信不久的未来人工智能会越来越厉害，这些问题可能也不复出现。

**但真正的问题是这些问题是否出现吗？**

不是的，真正的问题是**你是否拥有兜底的能力**。就目前的 AI 而言，我觉得它只适合干你能力范围内的事情。超出你能力范围的事情，就算 AI 给出回答你也无法判断对错，这在项目里面是不可取的。任何上线的错误都会导致直接的损失。

**健壮性、可维护性、容错率**，这三点对于一个程序来说是十分重要的。软件工程的本质是什么？我认为并不只是简单的写代码、编程序、跑项目。这是软件，但不是工程。工程能力是我觉得十分重要的能力，就算 100 年后也同样重要。它不是一种明确的技术，是一种眼界，是一种观念。

### 什么是软件工程？

我觉得应该拆开来说：**软件** 和 **工程**。

前者是写代码，是造砖块。我只需要保证这块砖的质量就可以。这是造砖工人的活计。
后者是系统工程，是盖高楼。我需要考虑很多东西，需要考虑能不能抗住台风和地震，需要考虑下水道建好之后能不能修理，需要考虑能承载多少人。这才是工程师，才是设计师。

我始终认为，软件工程的目的并不是培养出一个多么多么厉害的程序员。培养出一个 100% 无 Bug、代码效率极高、运用十分优雅、算法样样精通的程序员又怎么样？就像造砖厂，一个能造出十分优美、十分结实的砖块的工人，盖不出来摩天大楼。（当然，厉害的程序员的系统工程能力肯定不会差，这里只是比喻一种极端情况）

**而是培养出一名工程师，一名软件工程师！一个需要进行统筹规划的设计师！**

技术是会过时的。编程语言会更新，也许未来只用自然语言就可以编程（现在也快做到了），API 会变，框架会改，但什么不会变？  
(诚然,每个系统架构师都是从写出无数屎山的程序员成长起来的,底层的代码能力依然相当重要)

### **眼界与观念**

一百年前，人们建桥需要计算受力；如今建筑技术飞涨，人们建桥依旧需要计算受力。这是物理规律，是工程安全底线。软件工程何尝不是呢？眼界与观念就是人类对抗技术波动的锚点。

#### 什么是眼界？

*   **是全局视野**：写函数不能只盯着这个函数是不是能跑通，要注意这个函数在整个系统中扮演一个怎样的角色？负责怎么样的任务？
*   **是技术演进视野**：技术是工具而非牢笼。我们不应该被一种技术困住，而是要多学先进的新技术。不要拘泥于一种要被淘汰的旧技术.语言的语法或许不同，具体的参数和机制可能不同，但是你从中获得的能力是相通的。你在 C++ 中学到的内存管理思想和面向对象思想，到 Java 里面一样有用。要明白，思想是可以迁移的。
*   **是业务视野**：你写出一段优美到极致的代码，写了一堆极其牛逼的算法，但用户可能根本用不上。我们要明白这段代码是干什么的，是在什么情况下解决什么问题的，才能写出真正的好代码。

#### 什么是观念？

观念，是你在面对诱惑、压力、或者代码越写越烂时，内心坚守的底线和原则。

*   **工程底线观念**：代码能跑通并不意味着工程。这次跑通了，下一次换个环境换个参数还能跑吗？要学会问自己，如果用户输入了空值怎么办？如果内存不足、内存泄漏怎么办？对于健壮性的执念，就是观念。
*   **长期主义观念**：代码是给人看的，是给未来的自己看的。你现在认真写的每个变量名、函数名，写的每一行注释，都是在增援未来的自己。
*   **克制与取舍观念**：知道不做什么比知道做什么更加重要。不去写那些现在看起来高大上但根本用不到的复杂框架。知道为了项目的稳定性，该拒绝某些花哨但不成熟的新技术。
